# Основное

momentum — сервис одноразового обмена зашифрованными сообщениями и файлами.
Отправитель создаёт секрет локально → получает ссылку → передаёт её получателю любым каналом.
Сервер хранит только шифротекст; ключ (парольная фраза или ключ в фрагменте ссылки) существует только у отправителя и получателя.

## 1. Суть и цели

- Простой E2EE-обмен: текст, файл, текст вместе с файлом — одной ссылкой.
- Аккаунты, регистрация и профили отсутствуют.
- Минимальная инфраструктура: один процесс, одно хранилище-файл, самый дешёвый VPS.
- Минимальный цифровой след: на сервере только шифротекст и время жизни.

## 2. Функциональные требования

| # | Требование |
|---|---|
| F1 | Сообщение: текст ≤ 10 000 символов, файл ≤ 5 МБ, оба вместе |
| F2 | Шифрование и расшифровка — только на клиенте |
| F3 | Ключи существуют только на устройствах сторон; в ссылке только ID секрета, парольную фразу пользователь передаёт получателю вне сервиса |
| F4 | TTL: по умолчанию 24 часа, максимум 7 дней; по истечении — безвозвратное удаление |
| F5 | По умолчанию «сжечь после прочтения»: удаление сразу после первого чтения; TTL — верхняя граница срока жизни |
| F6 | Защита высокая по умолчанию и повышаемая: параметры Argon2id и алгоритмы версионируются в конверте |
| F7 | Доступ только по ссылке; ID секрета случайный, 128 бит → перечисление исключено |
| F8 | Режим передачи ключа на выбор: «ключ в ссылке» (по умолчанию) — 32-байтный ключ в URL-фрагменте, который браузер оставляет у себя; «фраза отдельно» — сгенерированная фраза передаётся получателю вне сервиса |

## 3. Модель безопасности

Защищено:
- компрометация или изъятие сервера → утекают только шифротекст и метаданные (ID, размеры, времена);
- администратор сервера → содержимое остаётся закрытым; сервер работает с непрозрачными блобами — расшифровка на клиенте;
- пассивный наблюдатель сети → HTTPS; в трафике к серверу только шифротекст и идентификаторы;
- оффлайн-перебор фразы по перехваченному шифротексту → словарная фраза 6–10 слов EFF (≈ 77–129 бит) поверх Argon2id (64 МиБ, t = 3): стоимость перебора растёт экспоненциально с числом слов; фраза генерируется клиентом из словаря — слабые пользовательские фразы отсутствуют.

Возможные векторы атак:
- канал доставки ссылки в режиме по умолчанию («ключ в ссылке») → полный доступ к секрету: мессенджер, облачная синхронизация истории, буфер обмена, браузерные расширения видят URL-фрагмент с ключом. One-time сгорание даёт обнаружение факта чтения (повторное открытие покажет «уже прочитан»). Защита от канала доставки — режим «фраза отдельно» (F8) с передачей фразы вторым каналом;
- режим «фраза отдельно»: передача фразы тем же каналом, что и ссылки, сводит защиту к одному фактору;
- компрометация устройства отправителя/получателя;
- активная подмена клиентского JS скомпрометированным сервером: владеющий сервером подменяет статику и получает ключ/фразу и содержимое при следующем открытии (пассивная компрометация раскрывает только шифротекст); митигации — self-host клиента или подписанные сборки;
- доступность: DoS или изъятие сервера останавливают сервис при сохранности данных; квота хранилища исчерпывается одним анонимным клиентом (30 POST/мин на IP × 8 МиБ ≈ 2 ГиБ за ~9 минут), IPv6-клиент с /64 обходит лимит по IP — сервис отвечает 507 до очистки;
- метаданные: `/status` раскрывает обладателю ссылки факт доступности секрета (для one-time — косвенно момент прочтения); сервер и наблюдатель видят длину шифротекста;
- удалённые записи восстановимы со страниц файла БД до ежедневного Rebuild, а также из бэкапов/снапшотов диска; гарантию даёт шифрование;
- первый визит до применения HSTS подменяем активным MITM; патчи рантайма попадают в self-contained бинарник при пересборке — возможен лаг от выпуска патча до перевыкладывания. Митигации: HSTS с `includeSubDomains`, отдельный поддомен, пересборка после Patch Tuesday.

## 4. Криптосхема

Версионированный конверт: `[magic][version][params][salt][nonce][ciphertext]`.
Параметры (алгоритм, настройки Argon2id) лежат в заголовке конверта — дефолты поднимаются сменой версии, старые ссылки читаются по своей.

v1 (зафиксировано):
- Два режима передачи ключа, одинаковый 42-байтовый layout — блобы режимов неразличимы по форме (наблюдатель и сервер видят одинаковые байты):
  - «фраза отдельно» (alg_id 0x01), ключ = Argon2id(фраза);
  - «ключ в ссылке» (по умолчанию, F8), alg_id 0x02: ключ 32 байта CSPRNG в URL-фрагменте `https://host/s/<id>#<base64url>`; в заголовке m/t/p = 0, salt — случайные неиспользуемые байты.
- Парольная фраза (режим 0x01): генерируется клиентом из EFF large wordlist (7776 слов), число слов выбирает создатель — 6–10 (по умолчанию 8 ≈ 103.4 бита; границы 6 ≈ 77.5 и 10 ≈ 129.3), разделитель «-», выбор слов CSPRNG с reject-семплированием. Фразу создаёт клиент — слабые пользовательские фразы исключены. Любой ввод нормализуется: trim → NFKC → UTF-8. Фраза остаётся на устройствах сторон.
- KDF: Argon2id, m = 65536 КиБ (64 МиБ), t = 3, p = 1 (второй профиль RFC 9106); salt 16 байт CSPRNG; ключ 32 байта. Ориентир: ≤ 0.5 с на десктопе, ≤ 2–3 с на средних смартфонах.
- Шифр AES-256-GCM (нативный WebCrypto), nonce 12 байт CSPRNG, тег 16 байт в конце шифротекста; AAD = весь заголовок конверта (режимы взаимно защищены от подмены).
- Внутренний payload: JSON `{ text?, file?: { name, mime, data(base64) } }`.
- Ссылка содержит ID (режим 0x01) или ID + фрагмент-ключ (режим 0x02).

Раскладка конверта v1 (целые little-endian, заголовок до шифротекста — 42 байта):

| Смещение | Поле | Размер | Значение |
|---|---|---|---|
| 0..3 | magic | 4 б | ASCII `MOMO` |
| 4 | version | 1 б | 0x01 |
| 5 | alg_id | 1 б | 0x01 = Argon2id(фраза), 0x02 = ключ из ссылки |
| 6..9 | m_kib | uint32 | 65536 |
| 10 | t | 1 б | 3 |
| 11 | p | 1 б | 1 |
| 12 | salt_len | 1 б | 16 |
| 13 | nonce_len | 1 б | 12 |
| 14..29 | salt | 16 б | CSPRNG |
| 30..41 | nonce | 12 б | CSPRNG |
| 42.. | ciphertext | остальное | payload ‖ GCM-тег (16 б) |

Передача ключа: фраза уходит получателю любым каналом вне сервиса (голос, другой мессенджер, лично).

Повышение надёжности (версии конверта):
- version → зарегистрированный набор {kdf, alg, m, t, p, длины}; парсер принимает только значения из набора;
- новая версия (+1, номер используется один раз) — единственный способ поднять дефолты; условие подъёма: новый набор укладывается в ~2–3 с на средних мобильных;
- writer пишет последнюю версию, reader поддерживает все предыдущие; старые ссылки читаются, сервер работает с блобом как с непрозрачным набором байтов.

## 5. Лимиты и валидация

- Текст ≤ 10 000 символов, файл ≤ 5 МБ; суммарный шифроблоб ≤ 8 МБ (запас на base64-оверхед ~33%).
- Лимиты проверяются дважды: на клиенте (UX) и на сервере (граница доверия).
- `ponytail:` v1 — base64 внутри JSON; сырой бинарный конверт появляется при росте лимита файла.

## 6. Хранение и TTL

- Хранилище: LiteDB (полностью managed — работает на любом glibc).
- Запись: `id (16 байт) | blob | expires_at | one_time | created_at`.
- Фоновая служба чистит просроченное раз в минуту, вычитая длины удаляемых записей из счётчика (полный пересчёт коллекции читал бы все блобы — до 2 ГиБ каждую минуту); ежечасно выполняет Checkpoint журнала, ежедневно — Rebuild файла БД.
- Квота хранилища: суммарный размер блобов ≤ `Vault:MaxTotalBytes` (2 ГиБ по умолчанию) плюс резерв свободного места диска (`DiskReserveBytes`, 512 МиБ); при превышении POST — 507. Все операции со счётчиком сериализуются в процессе; при старте записям без BlobLength проставляется длина и счётчик пересчитывается.
- One-time секрет: чтение с удалением в одной транзакции; блоб получает победитель удаления (DeleteMany > 0) — одно чтение, одна выдача.

## 7. API

- `POST /api/v1/secrets?ttl_minutes=N&one_time=bool` — тело: шифроблоб (octet-stream) → ответ: `id`
- `GET /api/v1/secrets/{id}` → `blob` (для one_time — транзакционно «прочитал-и-удалил»)
- `GET /api/v1/secrets/{id}/status` → флаг доступности; блоб остаётся на сервере, one-time секрет сохраняется
- Сервер трактует blob как непрозрачные байты.

## 8. Инфраструктура

- Один процесс: ASP.NET Core self-contained publish; статика веб-клиента из того же процесса (wwwroot). Без внешней БД, очередей, кэшей.
- TLS: nginx перед Kestrel; Kestrel слушает только localhost.
- Габариты: 1 vCPU / 512 МБ RAM / 5–10 ГБ диск → минимальный VPS справится.

## 9. Цифровой след

- Клиент полностью stateless: аккаунты, cookies и email отсутствуют.
- Access-логи выключены; в логах только ошибки без идентификаторов запросов.
- Рейт-лимиты — в памяти процесса.
- Клиент: все ассеты self-hosted, все запросы идут на собственный сервер (no CDN, no analytics, no внешние шрифты).
- HSTS с `includeSubDomains` (конфиг nginx); `preload` — осознанное решение оператора, [DEPLOYMENT.md](../DEPLOYMENT.md).
- Удаление по TTL/чтению — немедленное логическое удаление записи; фоновая чистка ежедневно выполняет Rebuild файла БД, возвращая страницы удалённых записей. До Rebuild, а также в бэкапах и снапшотах диска удалённые шифротексты восстановимы. Гарантию даёт шифрование: скопированный ранее шифротекст расшифровывается только при наличии ключа/фразы.
- Файл БД шифруется опционально (`Momentum__DatabasePassword`): пароль защищает содержимое (ID, размеры, времена) при утечке файла и снапшотов.

## 10. Стек (зафиксировано)

- Клиент: React Native → web (Expo SDK, TypeScript), WebCrypto + Argon2id (WASM); сборка — статический бандл.
- Сервер: C# / ASP.NET Core Minimal API + фоновый сервис чистки TTL; self-contained publish, один процесс.
